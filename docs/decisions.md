`/decide` 커맨드가 새 결정을 이 문서 하단에 append한다.

형식:

```

- 후보: A, B, C
- 선택: B
- 이유: ...
- 감수한 단점: ...
- 재검토 조건: (이 결정을 다시 봐야 할 상황이 있다면)
```

## [2026-09-14] Product/Inventory 재고 모델링 방식

- 이유: 한정 수량 판매 도메인에서 "어떤 유닛이 누구에게 선점되었는가"를 row 단위로 추적할 수 있어야
  선점/취소/재판매 흐름을 명확하게 설명 가능. 좌석 예매형 시나리오로 확장 시에도 모델이 자연스럽게 맞음.

  수량 카운터 모델보다 큼. 이번 프로젝트 스케일에서는 문제되지 않는다고 판단.
- 재검토 조건: 한 상품의 재고가 수만 단위를 넘는 대량 상품 시나리오를 다루게 되면 카운터 모델 병행 검토.

## [2026-09-15] InventoryUnit.reserve() 동시성 제어 락 전략
- 후보: A. 비관적 락(DB row lock, `SELECT ... FOR UPDATE`), B. 낙관적 락(`@Version`), C. Redis 분산락
- 선택: A. 비관적 락
- 이유: 한정 수량 상품의 "마지막 유닛을 여러 요청이 동시에 노리는" 상황은 hot-row 경합이
  전형적으로 발생하는 패턴이다. 낙관적 락은 경합이 심할수록 재시도가 폭증하는 구조라 이
  시나리오에서 가장 불리하다. 현재 배포는 단일 앱 인스턴스 전제(모듈러 모놀리식)이므로
  DB row lock만으로 정합성과 예측 가능한 처리량을 가장 단순하게 얻을 수 있고, 애플리케이션
  레벨 재시도 로직도 필요 없어 구현 복잡도가 가장 낮다.
- 감수한 단점: 경합이 심한 상품에서는 락을 잡은 트랜잭션이 끝날 때까지 다른 요청이 대기하므로
  응답 지연이 발생하고, 커넥션 풀 점유 시간이 늘어난다. 다중 WAS 인스턴스로 수평 확장하면
  DB row lock만으로는 부족해질 수 있다(Redis 분산락의 장점이 그때 비로소 실익이 됨).
- 재검토 조건: 다중 인스턴스 배포로 확장하거나, Waiting(대기열) 모듈과 락을 연계해야 하는
  시점에 Redis 분산락(C)으로 전환 검토. 그 전까지는 reserve 로직을 서비스 메서드 하나에
  캡슐화해 두어, 전환 시 변경 지점을 그 메서드로 한정한다(전략 패턴 등 사전 추상화는
  만들지 않음 — 2026-09-15 결정).

## [2026-09-15] confirm/cancel 요청 식별 방식
- 후보: A. `PurchaseAttempt.id`로 지정, B. `InventoryUnit.id` + `buyerId`로 지정, C. 별도
  예약 토큰(opaque token) 발급
- 선택: A. `PurchaseAttempt.id`
- 이유: reserve→confirm/cancel이 하나의 자원(attempt) 생명주기로 자연스럽게 이어지고,
  Purchase 모듈이 자기 리소스의 API 표면을 그대로 소유해 모듈 경계가 깔끔하게 유지된다.
  buyerId 값 비교만으로 소유권 검증도 부가 조건 없이 바로 처리할 수 있다. B는 유닛이
  CANCELLED→AVAILABLE로 재판매 사이클을 거치며 같은 unitId가 시간이 지나 다른 buyer의
  다른 시도를 가리킬 수 있어 "이 unitId+buyerId에 해당하는 최신 attempt" 조회라는 간접
  로직이 필요해진다. C(토큰 발급)는 이번 스코프(confirm/cancel API 하나)에 비해 과한
  인프라 추가로 판단했다.
- 감수한 단점: `attempt.id`가 순차 발급 Long이라 추측 가능하다. 더 근본적으로, 현재
  `buyerId`는 인증 시스템(User/Auth 모듈) 없이 요청 바디의 평문 문자열을 그대로 신뢰하고
  있어 "소유권 검증"이 실질적으로는 "값 일치 확인"에 가깝다 — 인증되지 않은 buyerId를
  스스로 주장하면 남의 attempt를 조작할 수 있는 구조적 한계가 있다(reserve()에도 이미
  있던 한계이며 이번 설계로 새로 생기는 문제는 아니다).
- 재검토 조건: User/Auth 모듈이 붙어 실제 인증이 도입되면, buyerId를 인증된 사용자
  식별자로 교체하고 소유권 검증 로직을 다시 점검한다.

## [2026-09-15] confirm/cancel 동시성 제어
- 후보: A. 비관적 락 재사용(reserve와 동일한 `SELECT ... FOR UPDATE`), B. 낙관적 락
  (`@Version`), C. 락 없이 상태 전이 검증(`transitionTo()`의 `IllegalStateException`)에만 의존
- 선택: B. 낙관적 락
- 이유: reserve()가 비관적 락을 택한 근거(여러 buyer가 같은 재고를 동시에 다투는 hot-row
  경합, 2026-09-15 위 결정)가 confirm/cancel에는 적용되지 않는다. 여기서는 이미 특정
  buyer가 선점한 유닛 하나를 다루므로, 문제가 될 수 있는 경합은 "같은 대상에 대한
  confirm/cancel이 드물게 동시에 들어오는 경우"뿐이다. 드문 충돌을 정확히 감지하는 것이
  목적이라는 점에서 낙관적 락의 교과서적 적용 조건에 더 가깝다고 판단했다. C는 같은
  트랜잭션 내 메모리 상태 기준 체크라 실제 동시 레이스는 막지 못해 제외했다.
- 감수한 단점: `InventoryUnit`(또는 `PurchaseAttempt`)에 버전 컬럼 추가가 필요하다. 충돌
  시 자동 재시도는 하지 않고 "현재 상태를 다시 확인하라"는 실패 응답으로 처리하기로
  했다. 이 선택은 벤치마크가 아니라 경합 패턴에 대한 논리적 추론에 근거한다 — 실제 충돌
  빈도나 지연 영향은 측정되지 않았다.
- 재검토 조건: 실제 운영에서 confirm/cancel 동시 충돌이 예상보다 잦아 재시도/실패 응답
  비용이 커지면 비관적 락(A)으로 재검토. 필요하면 `/bench`로 먼저 측정한다.

- 재검토 조건: 결제/환불 플로우가 도입되어 CONFIRMED 취소(환불)가 실제 도메인

## [2026-09-15] MySQL 테스트 프로필의 스키마 초기화 방식
- 후보: A. Hibernate `ddl-auto: create-drop`(H2와 동일 전략, datasource만 교체),
  B. Flyway/Liquibase 마이그레이션 도입 후 `ddl-auto: validate`, C. 정적 `schema.sql`
- 선택: B. Flyway
- 이유: 프로덕션 프로필(`application.yml`)은 이미 `ddl-auto: validate`로 스키마가
  별도로 존재한다고 가정하고 있는데, 정작 그 스키마를 만드는 마이그레이션 도구가
  프로젝트에 없었다(엔티티에서 파생되는 Hibernate 자동 생성에만 의존). 테스트 프로필만
  MySQL로 바꾸고 스키마 생성은 여전히 Hibernate 자동 생성(A)에 맡기면, "테스트가
  통과했다"는 신호가 프로덕션이 실제로 쓰는 스키마 관리 방식과는 여전히 무관하게 남는다.
  Flyway를 도입해 테스트에서 검증하는 스키마와 운영 배포 시 적용될 스키마 관리 방식을
  일치시키는 쪽을 선택했다.
- 감수한 단점: architect 서브에이전트는 이 결정이 "기존 테스트를 실제 MySQL 위에서
  통과시킨다"는 이번 세션 스코프를 넘어서는 신규 툴체인 도입(원칙 1/2/8 대상)이라고
  명시적으로 지적했다 — 마이그레이션 버전 관리라는 새 개념, 신규 의존성, 그리고 현재
  엔티티들을 역산해 baseline 마이그레이션 스크립트를 작성/유지해야 하는 부담이 생긴다.
  엔티티가 바뀔 때마다 대응하는 마이그레이션 스크립트도 함께 관리해야 한다. 이 단점을
  감수하고 B를 선택한 것은 사용자의 명시적 판단이다.
- 재검토 조건: 마이그레이션 스크립트 관리 부담이 엔티티 변경 빈도 대비 지나치게 커지면
  A(Hibernate 자동 생성)로 축소 검토.

## [2026-09-15] status 컬럼(InventoryUnit.status, PurchaseAttempt.status) 타입
- 후보: A. MySQL 네이티브 ENUM 유지(현재 `V1__baseline_schema.sql`이 채택한 형태, Hibernate가
  `@Enumerated(EnumType.STRING)`을 자동으로 이렇게 매핑함), B. `VARCHAR(20)` + Kotlin enum(검증
  책임을 애플리케이션 레벨로 위임)
- 선택: B. VARCHAR
- 이유: 이 프로젝트는 단일 애플리케이션만 이 DB에 쓰는 구조라, ENUM이 주는 DB 레벨 방어(다른
  소비자가 잘못된 문자열을 못 넣게 막는 것)의 실익이 낮다. 반대로 ENUM은 상태값을 추가할
  때마다 코드(Kotlin enum)와 DB(`ALTER TABLE ... MODIFY COLUMN`)를 이중으로 관리해야 하는데,
  이 동기화가 깨져도 `ddl-auto: validate`가 잡아주지 못한다는 걸 QA가 직접 실험으로 확인했다
  (ENUM 목록에서 값을 하나 빼도 39개 테스트 전부 통과 — 위 "MySQL 테스트 프로필의 스키마
  초기화 방식" 회귀 점검 참고). VARCHAR로 바꾸면 상태값 추가 시 스키마 변경 자체가
  필요없어져서 이 리스크가 구조적으로 사라진다.
- 감수한 단점: DB 레벨에서 잘못된 문자열이 저장되는 걸 막아주는 안전장치가 없어진다 — 검증
  책임이 전부 애플리케이션(`@Enumerated(EnumType.STRING)`)으로 넘어간다.
- 재검토 조건: 이 DB에 이 애플리케이션 외의 다른 쓰기 주체(별도 배치, 분리된 서비스 등)가
  생기면 ENUM이나 `CHECK` 제약 같은 DB 레벨 방어를 다시 검토한다.
- 구현 메모: 이번 세션에서는 기록만 하고 실제 마이그레이션(V2, `MODIFY COLUMN ... VARCHAR(20)`)은
  적용하지 않았다 — 원칙 2(범위 과다 금지)에 따라 다음 세션에서 별도 작업 단위로 진행한다.
- 적용 완료(2026-09-15): `V2__status_columns_to_varchar.sql`로 `inventory_unit.status`,
  `purchase_attempt.status`를 `VARCHAR(20) NOT NULL`로 전환. 값 자체(문자열)는 바뀌지 않아

  유닛이 0개(재고 소진)일 때만 "조건을 만족하는 행 없음"을 확정하려고 구간 끝(supremum)까지
  스캔하며 gap lock이 걸려 재입고 INSERT가 블로킹됨을 직접 확인했다(`LOCK_MODE =
  X,INSERT_INTENTION`/`WAITING`, `LOCK_DATA = supremum pseudo-record`). 그래서 최종 테스트는

  자체는 바뀌지 않았고, 어떤 재고 상태에서 시연되는지만 실측으로 구체화됐다. 상세 근거는

  39 + 신규 1) 테스트 통과 확인. CI(`twshop` 계정)에는 이 테스트가 필요로 하는

  추가했다. 유닛 3개(id 오름차순)를 만들고 앞 두 개를 reserve()로 RESERVED로 바꿔 세 번째만
  AVAILABLE로 남긴 뒤, `findAvailableForUpdate`가 그 세 번째 row를 찾아 잠근 채 커밋을

  `performance_schema.data_locks`에서 `LOCK_TYPE=RECORD`, `LOCK_STATUS=WAITING`,
  `LOCK_DATA=<그 row의 PK>`가 관측됐다 — status가 인덱스에 없어 `product_id` 인덱스로
  스캔하며 examine한 non-matching row까지 InnoDB가 잠근다는 ADR의 예상을 실측으로 확인했다.

  A2/A3 두 항목이 모두 마무리됐다. 프로덕션 코드(`InventoryUnitRepository`,
  `PurchaseService` 등)는 이번 작업에서도 변경하지 않았다.
- 후속 수정(2026-09-16, A3 flaky 리스크 제거): qa 검증에서 위 (1) `foundYLatch.await(500,
  TimeUnit.MILLISECONDS)`가 "CI에서 실측 안 된 이론적 flaky 리스크"로 지적됐다. 재검토해보니
  이 테스트의 실제 증명력은 (2)의 `assertEquals(-1L, commitInitiatedAtNanos.get(), ...)`(래치를
  메인 스레드가 쥐고 있어 레이스 없이 100% 보장)와 (3)의 `foundYAtNanos < commitInitiatedAtNanos`
  부등식, 이 두 결정론적 assertion만으로 이미 완결된다 — (1)은 있어도 없어도 결론에 기여하지
  않는 진단용 하한 체크였다. 그런데 500ms라는 타이트한 값 때문에 느린 CI 러너(GC 일시정지,
  커넥션 풀 경합 등)에서 실제로는 안 막혔는데도 우연히 타임아웃을 넘겨 테스트가 false
  failure를 낼 이론적 여지가 있었다. 원칙: **타이밍 assertion이 증명에 기여하지 않으면
  널널하게 풀고, 결정론적 체크만 증명을 전담하게 한다.** 이 파일의 다른 래치들과 같은 10초로
  늘렸다 — X를 붙잡는 2초보다 충분히 길어 정상 케이스에서는 항상 통과하고, 회귀 탐지력도
  줄지 않는다: 만약 누군가 실수로 product_id 필터를 없애 진짜 블로킹이 재발하면 Y는 X의
  커밋(2초 후)까지 기다렸다가 끝나므로 이 await는 여전히 true를 반환하지만, 그 시점엔 이미
  `commitInitiatedAtNanos`가 -1이 아니게 되어 바로 다음 줄의 `assertEquals`가 실패로 잡아낸다
  (테스트 코드 자체에 이 논리를 주석으로 남김). 로컬 MySQL 8.0에서 A3 단독 5회 연속 통과,
  전체 42개 테스트 회귀 없음 확인. 프로덕션 코드는 변경하지 않았다.
